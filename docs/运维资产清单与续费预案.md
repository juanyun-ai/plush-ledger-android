# 绒绒记账运维资产清单与续费预案

更新时间：2026-07-10

这份清单用于记录绒绒记账当前依赖的账号、域名、后端、静态站和发布资源。原则是：先维持现状，提前预警；能用低成本方案解决的问题，不急着上服务器或大套餐。

## 当前结论

1. Supabase 是当前比较主流的 BaaS / Postgres 后端平台，不是临时网盘。绒绒记账把它用作账号、数据库、对象存储和 Edge Function 后端，是合理路线。
2. 免费 Supabase 可以继续用，但不能当作“永久免费且无上限”的保险箱。需要监控容量、导出备份，并防止低活跃项目被暂停。
3. `xiaoxing.online` 是产品身份资产，建议续费。即使后续迁移云服务，域名也应该留住。
4. 火山引擎 TOS 资源包适合做 APK 镜像、分享卡片、官网素材和发布备份，不适合直接存用户账本数据库。
5. 官网和管理后台当前已通过 HTTPS 可访问，短期不需要迁移；后续重点是后台可观测、备份和下载镜像。
6. 2026-07-10 已确认 `app-releases` 中的 16 个 0.6.0-0.9.7 历史 APK 均不是当前更新源，并已删除该桶及其 369MB 历史对象。当前发布链路继续使用 GitHub raw / GitHub Release。

## Supabase 免费版边界

截至 2026-07-08，Supabase 官方价格页显示 Free 方案包括：50,000 月活用户、500MB 数据库、5GB egress、5GB cached egress、1GB 文件存储、2 个活跃项目限制，低活跃免费项目会暂停。官方文档还说明免费项目如果 7 天低活跃可能暂停，暂停后 90 天内可恢复；免费项目建议定期用 Supabase CLI `db dump` 导出数据。

参考：

- https://supabase.com/pricing
- https://supabase.com/docs/guides/platform/free-project-pausing
- https://supabase.com/docs/guides/platform/backups

对绒绒记账的影响：

- 当前用户量不大时，免费版足够撑住真实使用。
- 真正先到上限的通常不是用户数，而是数据库大小、Storage、下载/图片流量、函数调用和备份能力。
- 免费项目如果用户长期很少，存在被暂停的风险；App 和小程序如果没人打开，项目可能低活跃。
- 免费版没有 Pro 那种自动每日备份保障，必须做手动逻辑备份。

建议设置以下预警线：

| 指标 | 绿色 | 预警 | 动作 |
| --- | --- | --- | --- |
| 数据库体积 | < 300MB | >= 350MB | 检查表增长、清理日志、准备升级或归档。 |
| Storage | < 600MB | >= 800MB | 头像、导出文件、APK 不要继续堆在 Supabase。 |
| 月 egress | < 3GB | >= 4GB | APK、分享卡片迁到 TOS / CDN。 |
| 活跃项目 | 每天都有请求 | 连续 5 天极少请求 | 进入 Dashboard 或用健康检查产生少量真实请求。 |
| 备份 | 7 天内有导出 | 超过 14 天无导出 | 立刻做一次逻辑备份并保存到本地和私有对象存储。 |

## 火山引擎与域名续费判断

`xiaoxing.online` 建议续费。它已经进入 App 隐私政策、官网、后台、用户信任和备案叙事里，换域名的隐藏成本远高于每年几十到一百多元。

火山 TOS 资源包建议在到期前一个月再决定是否续费：

- 如果已用作 APK 镜像、分享卡片或项目素材，继续续小规格。
- 如果到期前仍完全没用到，可以取消自动续费，避免浪费。
- 不建议把 TOS 当核心用户数据库；它是文件桶，不是账本数据库。

最合适的利用方式：

1. APK 备用下载镜像，缓解 GitHub raw 对国内用户不稳定的问题。
2. 分享卡片、官网大图、安装包归档按需下载，降低 APK 体积。
3. 管理员私有备份：导出的数据库逻辑备份、审核材料、发布包、协议 PDF。

## 续费与迁移路线

### 现在到 2026-11

- 维持 Supabase Free、Cloudflare Pages、GitHub raw 下载。
- 分享卡片继续从 APK 内迁出，放在 `docs/share-cards/`，App 按需下载到本机缓存。
- 建立每月一次 Supabase 逻辑备份：已添加 `scripts/supabase_monthly_backup.sh`，并在本机安装 launchd 定时任务，每月 1 日 09:30 自动执行。
- 把火山 TOS 先作为备用资源，不急着开大套餐。
- 2026-07-09 检查 `app_versions`：当前有效 APK 主链路为 GitHub raw / GitHub Release，没有发现火山 TOS URL；TOS 暂未实际承载当前 APK 或分享卡片主流量。

### 2026-10 到 2026-11

- 检查火山 TOS 是否实际承载 APK / 图片。
- 检查 `xiaoxing.online` 域名到期日和自动续费状态。
- 如果 TOS 已承载发布资源，续小规格即可。
- 如果未使用 TOS，只保留域名/DNS，资源包到期不续也可。

### 触发升级 Supabase Pro 的条件

满足任一条件，再考虑升级：

- 数据库接近 500MB。
- 真实用户明显增加，不能接受免费项目暂停。
- 需要官方自动每日备份和更长日志保留。
- 管理后台开始承载真实运营，要求更稳定的后端可用性。

Pro 当前官方起价为 25 美元/月，超出“小成本玩具项目”的预算感受，所以不建议现在贸然升级。

### 未来迁移原则

- 不要为了焦虑迁移。迁移数据库比续域名、买小资源包麻烦得多。
- 真要迁移时，先迁静态大文件，再迁 APK 下载，最后才考虑迁核心数据库。
- 用户数据迁移必须先导出、校验、灰度，再切换；不能直接关旧服务。

## 管理后台优化方向

管理后台下一步不应该只是更“花”，而应该更像一个小型运维驾驶舱。

已新增方向：

- 管理后台增加“运维健康”页，展示数据库容量、Storage 分桶、最新版本下载承载、备份建议、每月和每季度维护清单。
- Supabase 增加 `public.admin_ops_stats()` 只给 `service_role` 使用的统计函数，后台通过 Edge Function 读取，不把管理权限暴露到浏览器。

继续优化：

1. 运维总览
   - 官网、后台、APK 下载、Supabase 函数健康状态。
   - 当前线上版本、最新 APK 文件大小、SHA-256、主备下载是否可访问。
   - Supabase 免费额度使用率：数据库、Storage、月流量、函数调用。

2. 备份与恢复
   - 显示最近一次备份时间。
   - 一键生成导出任务或至少提供明确操作入口。
   - 标记“超过 14 天未备份”的风险。

3. 到期提醒
   - `xiaoxing.online` 域名到期日。
   - 火山 TOS 资源包到期日。
   - 微信小程序版本审核/备案材料记录。

4. 发布中心
   - 版本号、更新说明、强制更新开关、APK 主备链接、文件大小、SHA-256。
   - 发布前自动检查：链接 200、文件大小匹配、SHA 匹配。

5. 数据质量
   - App / 小程序用户分渠道统计。
   - 新增、活跃、记账、反馈都只显示真实可证明数据。
   - 标出“旧版本未上报”的数据边界，不倒填假留存。

6. 安全审计
   - 管理员登录记录。
   - 关键配置修改记录。
   - 反馈回复、官方消息、版本发布的操作日志。

7. 用户关怀
   - 生日祝福候选列表。
   - 未处理反馈提醒。
   - 官方消息发送记录和送达/已读情况。

## 每月维护清单

- 打开 Supabase Dashboard，看数据库、Storage、流量、函数错误。
- 打开管理后台，看反馈、版本、活跃、异常。
- 访问官网、后台、APK 下载链接，确认 HTTP 200。
- 做一次数据库逻辑备份，并把备份放到本地和私有对象存储。
- 检查 GitHub release / docs 下载目录是否堆积过多旧 APK。
- 运行 `scripts/ops_maintenance_report.sh` 生成月度巡检报告，报告会落到 `reports/ops/`。
- 确认 `backups/supabase/` 最近 35 天内有成功备份包；Docker 未运行时会自动退到 JSON 快照模式。

## 每季度维护清单

- 检查域名、TOS、静态托管、Supabase 是否有账单或政策变化。
- 检查隐私政策、用户协议、账号注销说明是否仍与真实功能一致。
- 做一次恢复演练：确认备份文件能被读取，不只是“有备份文件”。
- 清理无用发布包、旧设计图、中间构建产物。
- 清理 `build/`、`app/build/`、根目录旧 debug APK、`build/release` 中的 unsigned/aligned 中间包。
- 检查 `docs/downloads` 与 GitHub Release：默认保留当前版本、上一版本和一个稳定回滚版本。
- 分享卡片、高清设计源文件和品牌源素材优先私有归档；生产仓库只保留 App 真实需要的压缩版本或远程缓存版本。

## 手机 App 用户数据 500MB 的判断

这不是正常的账本数据体积。按当前云端数据看，账本、日记、反馈这些核心业务表总量很小；手机端“用户数据”变成 500MB，更可能来自：

1. 旧版更新安装包残留：历史上多个版本 APK 接近 100MB，系统下载到 App 专属目录后，安装器打开成功会保留文件。如果连续下载几次，就可能堆到 300-500MB。
2. 分享卡片缓存：34 省分享卡片如果全部缓存，本地约 86MB。
3. 分享生成临时图片、头像缓存、导入文件预览等临时文件。

已做的修复：

- App 启动和新版本下载前会清理旧 `rongrong-ledger-*.apk` 更新包，只保留当前正在下载/安装的文件。
- 设置页“清理缓存”现在会同时清理内部缓存、分享图缓存、外部下载目录里的历史更新 APK；不会删除账本数据。

用户侧建议：

- 如果手机系统里显示绒绒记账用户数据异常偏大，先在 App 设置里点“清理缓存”。
- 如果仍然很大，再用系统设置清理应用缓存；不要点“清除数据”，否则本地模式用户可能丢本机数据。

## 我作为大管家的默认判断

当前最稳路线：

1. 继续用 Supabase 免费版承载账号和核心数据。
2. 继续用 Cloudflare Pages 托管官网和后台。
3. 续费 `xiaoxing.online`。
4. 火山 TOS 用来做文件镜像和备份，不直接存核心账本。
5. 先把管理后台补成真实运维面板，再考虑任何大迁移。

这套方案的优点是成本低、迁移少、用户体验不被折腾；风险是必须认真做备份和容量监控。
